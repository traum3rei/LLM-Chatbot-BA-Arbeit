\subsection{Auswahl der Embedding Modelle}
\label{s:konz:emod}
Nach der Auswahl des Chatmodelle geht es um die Auswahl des nächsten Modells.
Es wäre hier möglich das extra Einbettungsmodell weg zu lassen und es mit den 
Chatmodellen einbetten zu lassen. Damit der Vergleich zwischen den verschiedenen 
Chatmodellen nicht durch die Einbettungen beeinflusst wird, wird für alle 
Chatmodelle das selbe Einbettungsmodell verwendet.\par
Ebenfalls, wie bei den Chat Modellen werden hier Open Source Modelle benötigt, 
welche auf einem eigenen Server gehosted werden können.\par
Hierfür wird das Massive Text Embedding Leaderboard (MTEB) auf Huggingface betrachtet. 
Das MTEB Leaderboard sortiert Embedding Modelle nach ihrem durchschnittlichen Benchmark.
Es gibt zur Zeit der Verfassung dieser Arbeit keine Möglichkeit nach deutschen Modellen 
zu filtern. Daher wird das aktuell generell beste mehrsprachige Modell verwendet.
Aktuell ist das das "multilingual-e5-large-instruct" Modell, von intfloat, wer 
Teil von Microsoft Research in Asien ist. Dieses Model baut auf dem Model 
"xlm-roberta-large" von FacebookAI auf, bevor es MetaAI wurde. Das Model wurde finetuned
indem es mit 1 Milliarde Datensätzen kontrastiv vortrainiert wurde und im 
zweiten Schritt wurde es mit den Datensätzen, die für das E5-Mistral Model in der Arbeit 
"Improving Text Embeddings with Large Language Models" verwendet wurden, trainiert.

\section{Auswahl der Vektor Datenbank}
\label{s:konz:vec}
Als nächstes kommt die Auswahl der Vektordatenbank.
Für diesen Protoyp wird eine Vektordatenbank verwendet, die in einem Docker Container betrieben wird.
Im Bezug auf die Auswahl der Vektordatenbank werden drei Punkte beachtet.
\begin{enumerate}
    \item Open Source  
    \item Selbst hostbar
    \item Integration in Langchain
\end{enumerate}
Hierfür stehen die zwei Optionen Chroma und Milvus zur Verfügung.
Beide Optionen sind Open Source und selbst hostbar \cite{Chroma, HighPerformanceVectorDatabase}.
Beide Optionen erfüllen auch die zweite Anforderung und haben eine Langchain Integration \cite{VectorStoresLangChain}.
Durch die Integration innerhalb von Langchain, gibt es für beide Datenbanken innerhalb
der Entwicklung des Chatbots eine ähnliche Bedienung. Beide Optionen erfüllen die Anforderungen
die für die Vektordatenbank erstellt wurden. 
Aufgrund von persönlicher Erfahrung mit ChromaDB 
wir aus diesen Gründen ChromaDB für diesen Prototyp ausgewählt.

\subsubsection{Framework}
\label{s:konz:frame}
Bei der Auswahl der Konzeption für den Chatbot ist ein Frage, welches Framework verwendet werden soll.
Die drei Frameworks die zu Auswahl stehen wurden in \ref*{s:intr:frame} vorgestellt.
Haystack, Langchain und Llamaindex. Jedes 
der drei Frameworks ist nutzbar um einen nützlichen Chatbot mit RAG zu bauen. 
Bei allen drei gibt es die Möglichkeit mit RAG zu arbeiten und es ist ein Punkt
auf den sich alle drei Stück fokussieren \ref*{WhatHaystack, LlamaIndexLlamaIndex, IntroductionLangChain}. \par 
Die Punkte in Hinsicht auf das Framwork, welches verwendet werden soll, die beachtet 
werden sind die Langlebigkeit des Projekts und ebenfalls die Menge an Dokumentation und Support.
Da die Welt der LLM Systeme sich aktuell schnell ändert und viele neue Erkentnisse 
in der Forschung gesammelt werden, verändern sich auch die AI Frameworks mit den 
LLM Systemen zusammen \cite{naveedComprehensiveOverviewLarge2024}. Da das System möglichst 
langlebig sein soll und im besten Fall nur die einzelnen Bauteile, wie beispielsweise die 
LLM, mit der Zeit ausgetauscht werden sollten, ist es wichtig zu beachten, dass es ein 
Framework ist, welches möglichst lange bestehen bleibt und das Austauschen von einzelnen 
Teilen ohne großen Aufwand erlaubt. Dies hilft auch bei der Entwicklung bzw. Weiterentwicklung, 
da dadurch verschiedene Konfigurationen ausprobiert werden können ohne große Veränderungen
durchführen zu müssen.
 Die Community von Langchain ist die größte von den 
drei Framworks die in dieser Arbeit betrachtet werden, daher ist anzunehmen, dass der 
Support den man durch die Community erhält und die Menge an Dokumentation, die man finden
kann hierfür am größten sind. Eine Github Suche nach Haystack gibt uns 1.7k Ergebnisse. 
Eine Suche nach Langchain gibt uns 25k Ergebnisse. Und eine Suche nach LlamaIndex gibt uns
1.3k Ergebnisse. Eine Google Trends Analyse in diesem Bereich wäre vermutlich nicht
sehr aussagekräftig, da der Begriff Haystack von verschiedenen Unternehmen benutzt wird 
und dazu noch ein normal gebrauchtes Wort ist, daher werden wir uns an den Github Ergebnissen
orientieren, da auch, wenn dies möglicherweise nicht alle Projekte auflistet, es uns 
zumindest eine Orientierungsrichtung gibt. Langchain hat hier den Vorteil. \par
%relevant??
Das Austauschen von einzelnen Teilen des Systems scheint mit allen Frameworks ähnlich 
aufwändig zu sein. Kleinere Änderungen können aufgrund der Chains in Langchain, der
Pipelines in Llamaindex und der Pipelines in Haystack ähnlich leicht durchgeführt werden. 
Wenn man eine größere Änderung durchführen will, wie das
Ändern von einem simplen Text-System zu einem multimodalen System, welches ebenfalls 
mit Bildern arbeiten kann dann würde es relevant aufwändige Änderungen in allen
drei Frameworks erfordern. Daher wird hier angenommen, dass es bei allen drei Optionen
den gleichen Aufwand kosten würde.\par
Hinzu kommt, dass Langchain und Llamaindex bereits Datenladesysteme für Confluence haben, 
welches das System ist welches an die Vektordatenbank angebunden werden soll.
Dadurch, dass Langchain vielseitiger einsetzbar ist, als LlamaIndex und und Haystack, kommt der Vorteil dazu, 
dass Erfahrung mit dem Framework gesammelt werden kann und 
im Anschluss weitere Projekte, die über Chatbots und RAG Systeme hinaus gehen 
entwickelt werden können. Aus diesen Gründen wird Langchain für diese Projekt ausgewählt.\par 

\subsubsection{Nachrichten Historie}
Der Chatbot hat standardmäßig keine Erinnerungen oder Kontext außerhalb der 
aktuellen Anfrage, der RAG Dokumente und des Prompts. Falls man in einer Nachricht auf 
den Kontext in einer vorherigen Nachricht eingehen möchte und diesen 
nicht erwähnt, dann weiß der Chatbot nicht worum es geht.
Dies führt dazu, dass keine Folgefragen gestellt werden können, ohne 
dass der vorherige Kontext erklärt wird.\par
Um dieses Problem zu lösen muss eine Nachrichten Historie mit in das 
System eingebaut werden. Das Framework, Langchain, welches in \ref{s:konz:frame} festgelegt 
wurde, gibt einem die Möglichkeit eine Nachrichtenhistorie einzubauen.\par
Den abgespeicherten Chats muss eine Session ID gegeben werden, damit 
die Chats abgerufen werden können. \par
Chats innerhalb des Spaces werden innerhalb von Threads geführt.
Google gibt den Threads bereits eine ID. Da der Bot dieser 
Arbeit nur innerhalb dieses einen Saces arbeiten soll, 
wird diese ID verwendet um einen Python Hash Wert zu erzeugen,
welche als Session ID verwendet wird. Diese Herangehensweise funktioniert
nur innerhalb der Spaces, da die API über HTTPS-Server nicht in der Lage ist, auf 
Threads innerhalb von Einzelchats zu antworten.

\subsection{Datenupdates}
\label{s:konz:rag}
Hierbei geht es um das Thema des Hinzufügens von neuem Wissen zum Chatbot. Das Problem bei einem trainierten 
Modell ist es, dass es keine neue Information ohne ein neues Training in seine Wissensdatenbank aufnehmen kann. 
Da sich die Daten in den jeweiligen APIs ständig ändern können, stellt das ein Problem dar. Hier ist aber nicht 
nur neue Information ein Problem, sondern auch geänderte alte. Woher soll der Chatbot wissen, dass sich irgendeine 
Information, die bereits in der Wissensdatenbank vorhanden ist, geändert hat. Für das Problem von neuen Informationen 
gibt es hier zwei Optionen. Das Modell, auf dem der Chatbot aufbaut, könnte neu trainiert werden, mithilfe der neuen 
Informationen. Hier sind die Fragen, wie oft es neu trainiert werden soll, wie lange dieser Prozess dauert und wie viel 
dieser Prozess kostet. Wir können das Modell nicht bei jedem neuen Update neu trainieren. Das würde zu lange dauern, 
aber das heisst dass es einen Zeitraum gibt in dem der Bot nicht die aktuellsten Informationen hat. Wir benutzen hier 
die vorher bereits erwähnte RAG in Kombination mit einer Vektor Datenbank.\par
Welche RAG Variante benutzt wird, wird durch unser Framework, welches in \ref*{s:konz:bot} ausgewählt wurde,
bestimmt. Jedoch gibt es verschiedene Vektordatenbanken für die sich entschieden werden muss.

\subsection{Server}
\label{s:konz:ser}
Bei der Auswahl des Systems muss beachtet werden, dass die Techdivision den Server
für weitere AI Projekte verwenden will und daher ein System, welches den Chatbot
und die Datenbank betreiben kann ohne ausgelastet zu sein benötigt wird.\par
Das größte Modell, welches innerhalb dieser Arbeit verwendet wird, ist Phi-3 
Medium von Microsoft, welches 14 Milliarden Parameter hat. Die Menge 
an VRAM, die ein Modell dieser Größe in voller Präzision benötigt ist 
56GB VRAM. Die Standard Modelle, die von Ollama heruntergeladen 
werden, für diese Arbeit, sind 4 Bit quantisiert, wodurch die 
Anforderung auf 7GB VRAM sinkt. Die Uvicorn Worker, welche verwendet 
 werden um den FastAPI Server als Service zu betreiben brauchen 
 jeweils auch 2GB VRAM und RAM. Da der Server nicht alleine durch den Bot 
 ausgelastet sein soll, wird nach einem Server mit einer VRAM Größe von

Hierfür stehen zwei Optionen zur Verfügung. 
\begin{enumerate}

dedicated GPU Server, der bei Hetzner angeboten wird. 
Er hat einen Intel Core i5-13500 als CPU mit 6 Performance Cores und 
8 Efficient Cores. 64 GB DDR4 RAM, 2x 1.92 TB Gen3 NVMe SSDs und eine 
Nvidia RTX 4000 SFF Ada Generation mit 20GB GDDR6 ECC. 
Die Kosten für diesen Server wären maximal, wenn der Server 730 Stunden im Monat 
läuft, 218.96€ + 94.01€ einmalige Setupgebühr.\par
Diese Hardware ist ausreichend für die Anforderungen des Systems und ermöglicht

Wenn man einen ähnlichen Server in der Compute Engine von Google zusammenstellen

Der Hetzner Server, ist bei voller Nutzung ca 430€

\subsection{Anbindung Google Chat}
Die Anbindung an den Google Chat erfolgt über die Google Chat API.
Hierbei gibt Google den Nutzern vier Optionen dafür, wie man mit der API interagieren kann.\par
Die vier Optionen sind:
\begin{enumerate}
    \item App URL mittels https Server mit authentifiziertem SSL Zertifikat
    \item Apps Script Projekt 
    \item Cloud Pub/Sub
    \item Dialogflow
\end{enumerate}
Dialogflow ist keine Option, da hier nicht die Option besteht 
 eigene Open Source LLMs zu hosten und stattdessen die von Google 
angebotenen LLMs genutzt werden müssten, wodurch Anforderung A1 verletzt werden 
würde. \par
Apps Script ist auch keine Option, da bei Apps Scripts nur ein Skript ausgeführt wird, 
und keine vollwertige Umgebung zur Verfügung steht. Dies ist zu limitierend für 
diese Arbeit.\par
Da bereits ein HTTPS REST Server geplant ist, wird hier die App URL verwendet, wodurch
direkt mit der API interagiert werden kann und die API Calls, bei ankommenden Nachrichten, 
direkt an den Server gesendet. \par
Pub/Sub wäre eine Alternative, falls eine Firewall im Weg stehen würde, was hier aber 
nicht der Fall sein wird, daher ist dieser Zwischenschritt nicht notwendig. \par
\par
Für Google Chat gibt es die Möglichkeit Nachrichten synchron und asynchron zu versenden.
Für eine synchrone Nachricht muss die Antwort innerhalb von dreißig Sekunden an die API 
gesendet werden, nachdem eine Nachricht erhalten wurde. Für den Nutzen innerhalb 
dieser Arbeit wäre dies genug, aber über synchrone Nachrichte, gibt es keine Möglichkeit 
auf Threads zu antworten, stattdessen werden einzelne Nachrichten versendet. Da die Threads
benötigt werden, um einen sinnvollen Kontext für den Chatbot über die Nachrichtenhistorie 
zu erstellen, wird hier der asynchrone Ansatz gewählt.
