\section{Evaluierung}
Der finale Teil der Arbeit beschäftigt sich mit dem Vergleich der Performance,
des Systems. Das System wurde mit vier verschiedenen LLM Modellen implementiert und 
wird im ersten Schritt mit dem Framework RAGAS (siehe \ref{s:intro:ragas}) miteinander 
verglichen. Nach diesem Schritt werden die zwei bestabschneidensten Modelle 
für die finale Bewertung von Mitarbeitern aus der Techdivision miteinander 
verglichen. 

\section{RAGAS Vergleich}
Die erste Ausscheidungsrunde wird über das Benchmarking Frameworks entschieden.
Die vier LLM Modelle die hier zur Auswahl stehen sind finetuned von Metas Llama3,
Mistrals Mistral 2 und Googles Gemma. Dazu kommt noch die originale Version von 
Microsofts Phi 3.\par

\subsection{Testset}
Der erste Schritt für den Vergleich ist es Testsets herzustellen anhand
derer Ragas den Benchmark Test durchführen kann.\par
Die Variante die hierfür verwendet wird ist es einen TestsetGenerator per 
\par\verb+TestsetGenerator.from_langchain()+
herzustellen und mit diesem dann das Testset erstellen zu lassen.\par
Als Vorbereitung hierfür werden Daten benötigt. 
Die Daten die als Dokument geladen werden haben alle ein 
Metadata Dictionary. Damit der Generator erkennen kann,
welche Daten zusammengehören brauchen die Dokumente in 
diesem Metadata Dictionary ein Key Value Pair mit dem Namen
''filename``. Der Wert des ''filename`` Schlüssels wird verwendet 
um bei der Generation der Testdaten zusammengehörige 
Dokumententeile zusammenzufügen.\par
Nach dem Vorbereiten der Daten kann man damit beginnen den 
Generator zu erstellen.
Für diesen Generator werden drei Parameter verwendet.
Die \verb+generator_llm+, \verb+critic_llm+ und \verb+embeddings+.
Als Embedding Model benutzen wir ebenfalls das Model 
"intfloat/multilingual-e5-large", wie für den Chatbot und 
den Importer. 
\iffalse Als Critic und Generator LLM werden wir zwei verschiedene LLMs
nutzen.  Da die Geschwindigkeit der Erstellung dieser Daten
keine große Rolle spielt werden hierfür große Modelle genutzt.
Das Generator Modell wird eine auf Deutsch finetuned Version
von Mistrals Mixtral 8x7B sein und zwar 
"VAGOsolutions/SauerkrautLM-Mixtral-8x7B" \cite{VAGOsolutionsSauerkrautLMMixtral8x7BHugging2023}.
Als Critic Modell wird eine Version von Microsofts Phi 3 genutzt, welche
ebenfalls auf Deutsch finetuned wurde. Die Version die genutzt wird ist 
"VAGOsolutions/SauerkrautLM-Phi-3-medium", welche eine finetuned Version 
von dem Modell "unsloth/Phi-3-medium-4k-instruct" ist. \par\fi
Als Critic und als Generator LLM wird das 70 Milliarden 
Parameter Model Llama3 von Meta verwendet. 
Die Nutzung von Hugginface Modellen mit Ragas scheint aktuell 
nicht zu funktionieren, daher wird das Llama3 Model, welches 
man direkt über Ollama beziehen kann, verwendet.
Nach dem Erstellen des Generators und dem vor und aufbereiten der 
Daten kann man das Testset generieren lassen über die Funktion 
\verb+generate_with_langchain_docs()+. 
Für die Generierung kann man drei Parameter setzen.
Als erstes die \verb+documents+ von denen man die Testsets 
generieren will.
Hier werden Documents verwendet die über den \verb+ConfluenceLoader+
von Langchain geladen werden. Parallel wie beim Importer (\ref{s:dev:imp}).
Dazu kann man bestimmen, wie viele Elemente im Set enthalten sein sollen.
Diese \verb+test_size+ bestimmt wie viele Fragen vom \verb+TestsetGenerator+ generiert werden.
Dazu kann man die Verteilung der Fragen bestimmen.
Die Fragen die durch den Generator erstellt werden können dazu drei verschiedene
Typen haben. Diese drei Typen sind: \verb+simple+, \verb+reasoning+ und \verb+multi_context+.
Diese kann man der \verb+generate+ Funktion als dict mitgeben mit der Verteilung 
die man verwenden möchte. Hier werden diese Werte verwendet: \verb+simple: 0.5+,
\verb+reasoning: 0.2+ und \verb+multi_context: 0.3+.\par
Das Testset welches hierbei generiert wird kann man mittels 
\verb+to_pandas()+ als pandas Dataframe ausgeben.
Wenn man dieses Dataframe betrachtet sieht man, 4 relevante Spalten.\par
\verb+question+: Die Frage die dem Chatbot für das Benchmarking gestellt wird. \par
\verb+context+: Der Context aus dem die Frage erstellt wurde. \par
\verb+ground_truth+: Die Antwort auf die Frage. \par
\verb+question_type+: Der Question Typ, dessen Verhältnis in der \verb+generate+ Funktion bestimmt wurde.\par
Mit diesem Testset kann man nun die Chain bewerten.

\subsection{Evaluation}
\label{metrics}
Nachdem das Testset generiert wurde kann es zum bewerten
übergehen. Für die Bewertung gibt es acht verschiedene Metriken, die man 
betrachten kann. Hiermit kann man die verschiedenen Teile der Rag-Pipeline bewerten.
Im Folgenden werden die acht Metriken die zu Verfügung stehen betrachtet.
Standardmäßig verwendet die \verb|evaluate| Funktion die OpenAI API, 
dies kann überschrieben werden indem man der der Funktion ein \verb|llm| 
und ein \verb|embedding| übergibt. Man kann hierbei die Llm und das Embedding Model 
in \verb|LangchainLLMWrapper| und in \verb|LangchainEmbeddingsWrapper| verpacken,
falls man kein Langchain LLM oder Embedding verwendet. Wenn die LLM und das 
Embedding von Langchain ist, dann kann man diese direkt übergeben und sie werden 
in der Funktion verpackt.

\subsubsection{Faithfulness}
''Faithfulness`` zu Deutsch ''Genauigkeit`` ist die Metrik, die die 
generierte Antwort mit dem abgerufenen Kontext vergleicht. Dieser Wert ist 
eine Gleitkommazahl zwischen 0 und 1. Hierbei werden erst die Behauptungen 
aus der Antwort heraus gesucht und diese werden dann mit dem abgerufenen 
Kontext verglichen und es wird überprüft, ob die Behauptung aus dem Kontext 
gezogen werden kann.\par
Die Formel die hierfür verwendet wird ist wie folgt:
\[\text{Faithfulness score}= \frac{|\text{Anzahl der Behauptung die man aus dem Kontext schließen kann}|}{|\text{Gesamtzahl der Behauptungen}|}\]
\subsubsection{Answer relevancy}
''Answer relevancy`` zu Deutsch ''Relevanz der Antwort``, bewertet wie 
relevant die Antwort für die Eingabe ist. Hier werden Antworten
mit überflüssigen Informationen oder unvollständige Antworten 
geringer bewertet und Antworten die die Frage vollständig beantworten 
und keine überflüssigen Informationen beinhalten, werden höher bewertet.
Der Wert der Relevanz der Antwort kann zwischen -1 und 1, ist 
in der Praxis aber meisten zwischen 0 und 1 sein.
Die Formel die hierfür verwendet wird ist: 
\[\text{answer relevancy} = \frac{1}{N}\sum_{1}^{N}\cos(E_i, E_0)\]
\subsubsection{Answer semantic similarity}
Bei der Metrik ''Answer semantic similarity``, zu Deutsch ''Semantische Ähnlichkeit der Antwort``,
werden die \verb|answer| und \verb|ground_truth| miteinander verglichen.
Hierbei wird die Semantische Ähnlichkeit der beiden Werte gemessen.
Dieser Wert ist eine Gleitkommazahl zwischen 0 und 1. Ein höherer
Wert steht hierbei für eine höhere Genauigkeit. Hierfür wird das
embedding Model verwendet um die \verb|answer| und \verb|ground_truth| 
in Vektoren einzubetten und diese werden dann mittels Kosinus-Ähnlichkeit 
verglichen. Die Formel hierfür ist in \ref*{s:intro:semsea} 
bereits vorgestellt worden.

\subsubsection{Answer correctness}
Bei der Metrik ''Answer correctness`` oder zu Deutsch ''Korrektheit der Antwort``,
wird die Korrektheit der Antwort überprüft. 
Dieser Wert ist ebenfalls eine Gleitkommazahl zwischen 0 und 1.
Höhere Werte bedeuten hier eine höhere Korrektheit.
Hierfür werden \verb|ground_truth| und \verb|answer| miteinander
verglichen. Hierfür wird einmal die Semantische Ähnlichkeit 
betrachtet und dazu die faktische Ähnlichkeit. Diese Werte werden 
im Anschluss mittels einer gewichtet Formel 
benutzt um den Answer correctness Score zu erhalten.
\[\text{F1 Score} = \frac{|\text{TP}|}{(|\text{TP}| + 0.5 * (|\text{FP}| + |\text{FN}|))}\]
Wobei TP Richtig positive Fakten sind, Werte
die laut Antwort wahr sind und auch in der \verb|ground_truth|
enthalten sind.
FP sind falsch positive Fakten. Fakten die laut \verb|answer| wahr 
sind aber nicht in der \verb|ground_truth| enthalten sind.
FN sind falsch negative Fakten. Fakten die in der 
\verb|ground_truth| enthalten sind, aber nicht in der \verb|answer|.

\subsubsection{Context recall}
Die Metrik ''Context recall`` oder zu Deutsch ''Kontext Rückruf`` beurteilt, 
wie gut die abgerufenen RAG Dokumente mit der \verb|ground_truth| übereinstimen.
Der Wert kann zwischen 0 und 1 liegen. Hierfür werden die einzelnen 
Sätze in der \verb|ground_truth| mit den abgerufenen Dokumenten verglichen 
und es wird überprüft, ob man die Behauptungen in der \verb|ground_truth|
dem abgerufenen Dokument zuschreiben könnte.
\[\text{context recall} = \frac{|\text{Anzahl von Ground Truth Sätze die man von Dokumenten herleiten kann}|}{|\text{Anzahl von Sätzen in der Ground Truth}}|\]

\subsubsection{Context precision}
Die ''Context precision`` oder zu Deutsch ''Kontexgenauigkeit`` bewertet,
ob die Kontexte beziehungsweise die Dokumente in der \verb|contexts| Spalte,
die die \verb|ground_truth| beinhalten höher bewertet werden, als die jeweils anderen.
Hierfür werden die Spalten \verb|ground_truth|, \verb|question| und \verb|contexts| verwendet.\par
Der Context Precision Wert kann einen Wert zwischen 0 und 1 haben und höher 
bedeutet hier einen besseren Wert, wie bei den Werten zuvor.\par
Die Formel hierfür ist: 
\[\text{Context Precision@K}=\frac{\sum_{k=1}^{K}(\text{Precision@k} \times v_k)}{\text{Total number of relevant items in the top K results}}\]
\[\text{Precision@K}=\frac{(\text{true positives@k}}{(\text{true positives@k + false positives@k})}\]

Wobei $\mathbf{K}$ die Gesamtmenge der Kontexte in der \verb|contexts| Spalte
und \[v_k \in {0,1}\]

\subsubsection{Context relevancy}
Die ''Context relevancy`` oder zu Deutsch ''Kontextrelevanz`` bewertet den 
Relevanz des abgerufenen Kontexts. Dieser Wert fällt zwischen 0 und 1 und
hier ist ein höherer Wert besser. \par
Hierbei wird berechnet, wie viele Sätze der abgerufene Kontext beinhaltet,
die wichtige Informationen für die Beantwortung der Frage beinhaltet und dies 
wird durch die Gesamtzahl der Sätze im abgerufenen Kontext geteilt.

Die Formel hierfür ist: 
\[\text{context relevancy} = \frac{|\mathbf{S}|}{|\text{Total number of sentences in retrieved context}|}\]

\subsubsection{Context entity recall}
Beim ''Context entity recall`` oder zu Deutsch ''Kontext-Entitäts-Rückruf``
handelt es sich um die Metrik, die genutzt wird um zu vergleichen, wie viele 
Objekte im abgerufenen Kontext mit den Objekte in der \verb|ground_truth|
übereinstimmen.\par
Für diesen Wert werden die einzelnen Objekte in \verb|contexts| und in 
\verb|ground_truth| jeweils als Menge betrachtet und dann mittels einer logischen 
Überschneidung mit der Menge von Objekte \verb|ground_truth| verglichen.

Die Formel hierfür ist: 
\[\text{context entity recall} = \frac{|\mathbf{CE}\cap\mathbf{GE}|}{|\mathbf{GE}|}\]

\section{Umfrage Vergleich}
Hierfür wurden 5 Mitarbeiter aus dem Unternehmen mit einem Fragebogen 
ausgestattet und ihnen wurde Zugang zum System gegeben. 

\subsection{Fragebogen}
Der Fragebogen wurde so erstellt, dass es keine genauen Fragen gibt, 
sondern nur Themengebiete, die abgefragt werden sollen. Das wichtige 
beim Auswählen der Themengebiete war, dass es Informationen waren, die 
auf der Confluence Instanz, auf die der Chatbot Zugriff hatte, verfügbar 
waren. Die Confluence Instanz die für diese Arbeit verwendet wurde ist ein 
Testsystem auf das für diese Arbeit verschiedene Blogeinträge und Dokumentationen 
geladen wurden, die den Einträgen auf dem Produktivsystem ähneln nur ohne kritische 
Kundendaten und ähnliches. Die Fragen für den Fragebogen werden aus diesen neu erstellten 
Einträgen erstellt. \par
\par


Folgende Aufgaben wurden den Teilnehmern gegeben:

\begin{enumerate}
    \item Wie richten sie die VPN ein? Lassen sie sich eine Anleitung dazu ausgeben.
    \item Wie lösen Sie bei aktiven VPN zur TD das Problem von DNS Auflösung?
    \item Welche Möglichkeiten gibt es zum Teilen von sensitiven Daten?
\end{enumerate}
Die den Teilnehmern gegeben Aufgaben decken unterschiedliche 
Kompetenzen des Chatbots ab.\par
Frage 1, die Einrichtung der VPN: Der Chatbot sollte in 
der Lage sein, eine klare, schrittweise Anleitung zur 
VPN-Einrichtung aus dem Confluence-Wissen zu extrahieren 
und dem Teilnehmer präsentieren.\par
Frage 2, DNS-Auflösungsproblem bei aktivem VPN:
Hier sollte der Chatbot Problemlösungsstrategien aus 
dem Confluence ableiten und dem Benutzer mögliche
 Lösungsansätze vorschlagen.\par
Frage 3, Teilen sensitiver Daten:
Der Chatbot sollte verschiedene in Confluence 
dokumentierte Methoden zum sicheren Datenaustausch 
identifizieren und dem Benutzer erklären können.\par

Die Teilnehmer sollten die Antworten auf einer Skala von 1-5 für beide 
LLMs bewerten. wobei 1 für sehr schlecht und 5 für sehr gut steht.
